Plate 00

目录结构

17 个源文件,每个文件只装一小撮互相配合的类——不是一类一文件,是一个内聚概念一文件。

  • src/role_runtime/
    • types.py共享类型别名,零内部依赖
    • constants.pyMCP 协议版本号等常量
    • errors.py9 个异常类,一条继承链
    • context.pyContextNode · CompileLevel — 渐进披露的统一契约
    • skill.pySkill
    • data.pyDataSource · DataBinding · DataProvider 等 7 个
    • role.pyRole — 递归组合的团队树
    • registry.pyRoleRegistry — 路径解析 + 环检测
    • compiler.pyRoleCompiler — 渐进披露编译器
    • runtime.pyRoleRuntime — 执行边界,二次授权
    • mcp/
      • models.pyMCPTool · MCPServer · ToolAnnotations
      • binding.pyMCPBinding — 最小权限关系对象
      • protocol.pyJSON-RPC 2.0 消息构造
      • transport.pyMCPTransport 接口 + 两种实现
      • client.pyMCPClient — 串起 protocol + transport
  • examples/kubernetes_team.pyk8s 排障 / 运维双角色示例
  • tests/17 个单测,全部通过
  • docs/01-role-object-model.md设计推导文档

Plate 01

层级地图

按实际 import 语句追出来的依赖图——六层,单向,零循环。

role_runtime/__init__.py 和 mcp/__init__.py 没画进去——它们只做 re-export,不参与依赖方向,是给外部用的统一导入入口。

Plate 02

对象模型

四个 ContextNode 子类共享同一套 route / active 生命周期;MCPServer 被有意排除在外。

MCPBinding 和 DataBinding 是结构上同构的两个关系对象(都是"Role 到某个外部资源的最小权限视图"),但物理位置不对称——前者单独在 mcp/binding.py,后者揉在 data.py 里。目前 data.py 只有 145 行,还没到必须拆分的复杂度。

Plate 03

编译路径 — LLM 看见什么

RoleCompiler 只读,不执行。默认只吐 route 卡片,选中的能力才展开成 active 细节。

Plate 04

执行路径 — 二次授权怎么挡下来

context 里看不见的工具早被挡在外面;RoleRuntime 假装不知道这件事,执行前重新查一遍。

同一套检查,两个入口。 read_data / write_data 走的是完全平行的逻辑——write_data 永远要求 approved=True,没有"read-only 就放行"这条捷径,因为写操作没有天然安全的子集。
