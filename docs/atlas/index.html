不是一类一文件,是一个内聚概念一文件。 v0.0.2 那个塞了四个类的 mcp/models.py 先按概念拆成三个文件,ADR 003 之后其中两个概念整体消失, 只剩 tools.py 与 resources.py 各装一个类。

两个"唯一"是硬约束,不是习惯:targets/writer.py 是唯一写文件系统的模块, server/ 是唯一 import 官方 SDK 的层。 tests/test_layering.py 用 AST 遍历全包来强制第一条,还顺带确认没有任何模块碰网络; 第二条额外在子进程里真跑一次:import contexture.core 之后 sys.modules 里不许出现 mcp。

Plate 01

分层地图

五层单向依赖,外加一条副路。主路走到 server,Agent 从那里连进来。core 不许 import mcp——一个伸手去够线路协议的对象模型,已经不是对象模型了。

为什么 SDK 是硬依赖而不是可选 extra。 2026-07-28 这版协议不小: 取消了 initialize 握手,改成每请求 _meta 协商 + 强制的 server/discover,还得同时服务四个更老的修订。自己扛这些没有回报。 做成硬依赖而不是 [server] extra,是因为 server 现在就是产品本身—— 把产品做成可选自相矛盾。代价写在明处:28 个包、37MB、零依赖属性没了。

但 core 仍然干净。 导入 facade 不会加载 server 层, 也不会加载 SDK。只想建模上下文的项目,只付建模的钱。

Plate 02

文件依赖

按实际 import 语句追出来的图。core/ 内部仍是那条干净的 DAG,上面三层各挂各的。

各层的 __init__.py 没画进去——它们只做 re-export,不参与依赖方向。 注意没有任何一条箭头从上层指回 core:这条约束由一个测试守着, 导入 contexture.core 后检查 sys.modules 里不含任何上层模块。

Plate 03

对象模型

四个 ContextNode 子类共享同一套 route / active 生命周期,而且只有这四个。Role 的每个字段都是"它自己声明的东西"——没有第二条腿。

这张图删过两轮。v0.0.1 里 Role 挂着 mcp_bindings 和 data_bindings 两条结构同构的授权线;d2a8e66 把后者并进 Resource 消掉一条;ADR 003 把前者整条拿掉——它描述的是"别人家的能力", 而 Contexture 是提供方,不是宿主。

Resource 的关键约束不在 route/active 之分,而在 descriptor 与 content 之分:两个编译层级都只吐元数据, 字节只能由 resources/read 触发 read() 拿到。 列出一百份 runbook 花的是一百行描述,不是一百份文档。

Plate 04

声明式前端 — 一个类体怎么变成 Role

业务用自己的词汇写一个类,框架在类创建时把它变成 Declaration 并校验。出错在 import 时就炸,不等到第一次用。

这没有违背"组合优于继承"。 两个机制回答不同问题: class K8sOperator(Role) 说的是这个节点是什么, children=[...] 说的是它持有什么。继承从不表达包含关系—— 声明式角色协调其他角色时,一样把它们放进 children。

两个 slots 陷阱。 @dataclass(slots=True) 会重建类对象, 于是:① __init_subclass__ 里的零参 super() 抛 TypeError(__class__ 单元格指向被丢弃的旧类);② getattr(cls,'name') 返回槽描述符而非 None。 两处都不是看代码能看出来的,所以在源码里各留了一条注释。

Plate 05

多目标渲染 — 声明一次,三种表达

这是 v0.0.3 的核心价值:同一棵 Role 树进去,三种 Agent 各自能读的文件出来,并如实报告每个目标丢了什么。

render() 从不写盘,只返回 ArtifactSet(路径 + 内容 + 摘要)。 全包只有 targets/writer.py 碰文件系统,而 ADR 003 之后没有任何模块碰网络—— 线路整个交给了官方 SDK。这两条同样有测试守着(基于 AST,不是字符串匹配)。

摘要是内容哈希,所以"已安装的产物是否已经漂移"可以直接比对得出; writer 也据此跳过内容未变的文件,不去无谓地改动时间戳。

Plate 06

编译路径 — LLM 看见什么

RoleCompiler 只读,不执行。默认只吐 route 卡片,选中的 Skill 才展开成 active 细节。

Plate 07

MCP 投影 — 声明怎么变成扁平的 MCP 表面

这是 v0.0.4 的核心转换。server/projection.py 是全仓库唯一知道线路长什么样的地方,而它不含任何业务规则——它做的全部事情就是翻译。

read_only 走 annotation,永远不走参数。 它是宿主的可信分类,投影成协议的 readOnlyHint,让 host 决定要不要先问人。 如果它变成一个 input schema 里的字段,模型就能自己填 approved=true—— 模型批准自己的写操作,那不叫批准。 tests/test_stdio_server.py 里有一条断言在真实线路上守着这件事。

一个真实的坑。 @dataclass(slots=True) 做返回类型时, pydantic 会把 slot 描述符读成"不可序列化的默认值",output_schema 静默变成 None, structured_content 变成 null——不报错,只是结果没了。 demo 里的 PodStatus 因此不带 slots,代码旁边有注释写明原因。

Plate 08

披露路径 — Agent 怎么在树上走,而服务器不记状态

MCP 2026-07-28 规范原文:tools 列表 MUST NOT 因连接、或因同一连接上的其他请求而变化。所以树不能是协议表面——它得活在 payload 里。

一个进程服务整片森林。 既然树在 payload 里、discover 负责路由, 就没必要在启动时用 --root-role 钉死一个根。 N 个叶子 role 仍然是 1 个进程,不是 N 个。
披露 ≠ 授权,这个区分必须认下来。 业务 tool 全在 tools/list 里,agent 完全可以跳过导航直接调——你拦不住,也不该拦。 扁平表面上按 role 的硬授权做不到,这是协议决定的,不是设计取舍。

渐进式披露交付的是知识,不是访问权。 tool 能调,但"该按什么顺序看证据""exit 1 和 exit 137 怎么区分""为什么不能先重启"—— 这些只在 get_context 之后才存在。 所以验收标准不是"证明 agent 调不到 tool",而是 "证明 Skill 全文只在 get_context 之后才进入上下文"。
