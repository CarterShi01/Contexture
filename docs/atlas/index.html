Plate 00

分层地图

五层单向依赖。只有 core 是必须的——想要生成上下文文件的项目,永远不会加载一个 transport。

为什么包要改名。 叫 role_runtime 的时候,runtime 就是产品全部。 在新定位下 runtime 是可选层、模型才是产品,包名指向了最不核心的部分。现在叫 contexture,与项目名和定位一致。

Plate 01

文件依赖

按实际 import 语句追出来的图。core/ 内部仍是那条干净的 DAG,上面三层各挂各的。

各层的 __init__.py 没画进去——它们只做 re-export,不参与依赖方向。 注意没有任何一条箭头从上层指回 core:这条约束由一个测试守着, 导入 contexture.core 后检查 sys.modules 里不含任何上层模块。

Plate 02

对象模型

四个 ContextNode 子类共享同一套 route / active 生命周期;MCPServer 被有意排除在外。一个 MCPBinding 同时管住 tool 和 resource 两条授权线。

v0.0.1 的图里,Role 同时挂着 mcp_bindings 和 data_bindings 两条平行的授权线,MCPBinding 与 DataBinding 结构同构却分居两处。现在 MCPBinding 一个类同时持有 allowed_tools 和 allowed_resources, 那道不对称消失了。

MCPResource 的关键约束不在 route/active 之分,而在 descriptor 与 content 之分:两个编译层级都只吐元数据,内容永远只能由 RoleRuntime.read_resource() 取。

Plate 03

声明式前端 — 一个类体怎么变成 Role

业务用自己的词汇写一个类,框架在类创建时把它变成 Declaration 并校验。出错在 import 时就炸,不等到第一次用。

这没有违背"组合优于继承"。 两个机制回答不同问题: class K8sOperator(Role) 说的是这个节点是什么, children=[...] 说的是它持有什么。继承从不表达包含关系—— 声明式角色协调其他角色时,一样把它们放进 children。

两个 slots 陷阱。 @dataclass(slots=True) 会重建类对象, 于是:① __init_subclass__ 里的零参 super() 抛 TypeError(__class__ 单元格指向被丢弃的旧类);② getattr(cls,'name') 返回槽描述符而非 None。 两处都不是看代码能看出来的,所以在源码里各留了一条注释。

Plate 04

多目标渲染 — 声明一次,三种表达

这是 v0.0.3 的核心价值:同一棵 Role 树进去,三种 Agent 各自能读的文件出来,并如实报告每个目标丢了什么。

render() 从不写盘,只返回 ArtifactSet(路径 + 内容 + 摘要)。 全包只有 targets/writer.py 碰文件系统,只有 protocol/transport.py 碰网络—— 这两条同样有测试守着(基于 AST,不是字符串匹配)。

摘要是内容哈希,所以"已安装的产物是否已经漂移"可以直接比对得出; writer 也据此跳过内容未变的文件,不去无谓地改动时间戳。

Plate 05

编译路径 — LLM 看见什么

RoleCompiler 只读,不执行。默认只吐 route 卡片,选中的能力才展开成 active 细节。

Plate 06

执行路径 — 二次授权怎么挡下来

context 里看不见的工具早被挡在外面;RoleRuntime 假装不知道这件事,执行前重新查一遍。

Resource 读走同一条路,但少一道闸。 read_resource() 同样解析 binding、 同样二次校验白名单,但没有审批环节——MCP 协议里 Resource 天生只读,不存在 resources/write,所以"在不在 allowed_resources 里"就是全部授权。 这也是为什么 MCPBinding 有 read_only_tools 却没有 read_only_resources。
