Plate 00

目录结构

16 个源文件,每个文件只装一小撮互相配合的类——不是一类一文件,是一个内聚概念一文件。

  • src/role_runtime/
    • types.py共享类型别名,零内部依赖
    • constants.pyMCP 协议版本号等常量
    • errors.py9 个异常类,一条继承链
    • context.pyContextNode · CompileLevel — 渐进披露的统一契约
    • skill.pySkill
    • role.pyRole — 递归组合的团队树
    • registry.pyRoleRegistry — 路径解析 + 环检测
    • compiler.pyRoleCompiler — 渐进披露编译器
    • runtime.pyRoleRuntime — 执行边界,二次授权
    • mcp/
      • models.pyMCPTool · MCPResource · MCPServer · ToolAnnotations
      • binding.pyMCPBinding — tool 与 resource 的最小权限关系对象
      • protocol.pyJSON-RPC 2.0 消息构造
      • transport.pyMCPTransport 接口 + 两种实现
      • client.pyMCPClient — tools/* 与 resources/* 的调用方
  • examples/engineering_team.pyKubernetes + GitHub 双 Server、三角色示例
  • tests/32 个单测,全部通过
  • docs/01-role-object-model.md设计推导文档

v0.0.1 里的 data.py 已删除。它装的 7 个类(DataSource、DataBinding、 DataProvider 等)构成了第二套最小权限系统,与 MCPBinding 回答同一个问题; 现在统一由 MCP Resource 承担。

Plate 01

层级地图

按实际 import 语句追出来的依赖图——六层,单向,零循环。

role_runtime/__init__.py 和 mcp/__init__.py 没画进去——它们只做 re-export,不参与依赖方向,是给外部用的统一导入入口。

Plate 02

对象模型

四个 ContextNode 子类共享同一套 route / active 生命周期;MCPServer 被有意排除在外。一个 MCPBinding 同时管住 tool 和 resource 两条授权线。

v0.0.1 的图里,Role 同时挂着 mcp_bindings 和 data_bindings 两条平行的授权线,MCPBinding 与 DataBinding 结构同构却分居两处。现在 MCPBinding 一个类同时持有 allowed_tools 和 allowed_resources, 那道不对称消失了。

MCPResource 的关键约束不在 route/active 之分,而在 descriptor 与 content 之分:两个编译层级都只吐元数据,内容永远只能由 RoleRuntime.read_resource() 取。

Plate 03

编译路径 — LLM 看见什么

RoleCompiler 只读,不执行。默认只吐 route 卡片,选中的能力才展开成 active 细节。

Plate 04

执行路径 — 二次授权怎么挡下来

context 里看不见的工具早被挡在外面;RoleRuntime 假装不知道这件事,执行前重新查一遍。

Resource 读走同一条路,但少一道闸。 read_resource() 同样解析 binding、 同样二次校验白名单,但没有审批环节——MCP 协议里 Resource 天生只读,不存在 resources/write,所以"在不在 allowed_resources 里"就是全部授权。 这也是为什么 MCPBinding 有 read_only_tools 却没有 read_only_resources。
