Contexture Atlas

一份把框架拆开看的地图集——业务怎么声明一次、分层谁依赖谁、类怎么组合、同一份声明怎么变成一个 Claude Code 和 Codex 都能连的原生 MCP Server。

16 框架源文件· 23 个类· 4 层单向依赖· 112 个测试用例· MCP 2026-07-28

v0.0.4 变更：主箭头翻转了。v0.0.3 的主线是 声明 → 编译 → 生成 CLAUDE.md / AGENTS.md / SKILL.md → Agent 去读文件； v0.0.4 的主线是 声明 → 一个原生 MCP Server → Agent 连上来。 生成的文件是副本,声明一变就漂;server 是指针,不会漂。

新增 contexture.discovery(ref 寻址与两个动词)与 contexture.server(唯一 import 官方 SDK 的层); core 新增可执行的 Tool 与可读的 Resource。 targets/ 降级为副路。 代价:零依赖属性没有了,官方 SDK 带进 28 个包。

随后出站方向被整体移除(ADR 003)。 MCPTool / MCPResource / MCPServer / MCPBinding / protocol/ / execution.py 描述的是"别人家的能力"和"怎么去调它"——那是宿主该干的事,不是提供方。 删掉之后 core 只剩四个概念,且真的不知道 MCP 存在。
v0.1.0 变更:能力不再上 MCP 表面(ADR 004)。 在此之前,projection 把整片森林的每一个 tool 和 resource 都注册成原生 MCP 条目。注册即常驻——协议禁止 tool 列表随连接变化,所以一个被注册的能力 是每次会话无论用户问什么都要付的钱。渐进披露实际只藏住了 instructions。

现在表面是固定五个工具:contexture_discover · contexture_open · contexture_read · contexture_invoke_read_only · contexture_invoke。 业务能力的名字、描述、schema 只活在 payload 里,打开它所属的角色时才到达。 invoke 拆成两扇门,是 readOnlyHint 在网关下唯一的活法: 宿主看不见业务 tool 了,但看得见走的是哪扇门,而门与 ref 不一致的调用被拒绝而不是被执行。

披露按种类切而不是按深度:角色骨架一次给全(它没有 schema,便宜), 角色里的东西等被打开。ContextTree 一个类接替了 discovery.py + compiler.py + core/registry.py, 八个类变一个。代价也记在 ADR 004 里:业务 tool 的 outputSchema 没了, 而且模型对泛化 dispatch 的熟练度不如原生 tool call。
v0.2.0 变更:副路整条删除(ADR 005)。 ADR 001 把主箭头翻转之后,contexture.targets 没有被删,只是降级成"给连不上 MCP 的 runtime"的副路。量一下:框架里没有任何模块 import 它,CLI 里 没有任何命令通向它(只有 new / list / serve / demo), 脚手架不提它,用户唯一的入口是照着 README 的一段散文手写 import render_all。

七个文件、740 行、十个类——占当时框架类数的三成——外加 244 行测试,谁都到不了。 一个没人能调用的能力不叫"留着",叫"在付钱"。

删掉之后:TargetRenderError 从公开门面消失(破坏性变更), core/errors.py 剩下的五个异常都有活着的代码会抛; cli.py 成为全包唯一碰文件系统的模块,而且只用来生成项目—— "从声明到线上这条路上没有任何模块开过文件",这条断言比原来那条强。
v0.2.0 变更:异常携带事实,文案收归一处(ADR 006)。 问"server 这层到底解决什么问题"问出来的:它不是翻译层——真只是翻译的话八十行就够了。 它装着三样变更理由完全不同的东西,而「agent 读到什么」这一样没有模块,于是散了。

症状:每个网关工具有两份描述(docstring 与 add_tool 的 description), 上线的是较差那份;"用卡片上的 ref、别自己拼"这句话有三个措辞不同的副本。 更要命的是最该说的那半句根本写不出来——查找失败在 tree 里抛出, 而"下一步该调 contexture_open"需要网关工具的名字,tree 不知道也不许知道。

根因是一个字符串伺候两个读者:看 traceback 的开发者,和会读错误并自己改正的模型。 现在 NodeNotFoundError 只携带事实(reason · ref · segment · scope · kind · known), 异常本身就是向上运输结构化数据的通道,不需要注入任何回调; projection._translated 本来就是唯一的收口,以前被塞成品字符串,现在拿到事实自己渲染。 六种失败每一种都以"该调哪个工具"收尾,有穷举测试守着。

Role 也拿回了它本该有的方法:member() 跨种类查找——因为跨种类唯一这条不变量本来就是它自己在强制的, 它付了代价却把好处让给了 tree._member(那个函数的签名里没有一个 tree 概念)。 NodeNotFoundError 不再继承 KeyError,四个 get_* 退休。

Plate 00

目录结构

不是一类一文件,是一个内聚概念一文件。 v0.0.2 那个塞了四个类的 mcp/models.py 先按概念拆成三个文件,ADR 003 之后其中两个概念整体消失, 只剩 tools.py 与 resources.py 各装一个类。

八个类变一个。compiler.py 的四个类、discovery.py 的三个类、 core/registry.py 的一个,现在是 tree.py 里的 ContextTree。按 README 自己那条准入测试问——"它帮业务开发者定义能力, 还是帮框架运行能力"——被删掉的那些两边都不沾。

两个"唯一"是硬约束,不是习惯:cli.py 是唯一写文件系统的模块—— 而且只在 contexture new 生成项目时写,从声明到线上这条路上没有任何模块开过文件; server/ 是唯一 import 官方 SDK 的层。 tests/test_layering.py 用 AST 遍历全包来强制第一条,还顺带确认没有任何模块碰网络; 第二条额外在子进程里真跑一次:import contexture.core 之后 sys.modules 里不许出现 mcp。

Plate 01

分层地图

三层单向依赖,上面骑一个命令行,没有旁路。主路走到 server,Agent 从那里连进来。core 不许 import mcp——一个伸手去够线路协议的对象模型,已经不是对象模型了。

为什么 SDK 是硬依赖而不是可选 extra。 2026-07-28 这版协议不小: 取消了 initialize 握手,改成每请求 _meta 协商 + 强制的 server/discover,还得同时服务四个更老的修订。自己扛这些没有回报。 做成硬依赖而不是 [server] extra,是因为 server 现在就是产品本身—— 把产品做成可选自相矛盾。代价写在明处:28 个包、37MB、零依赖属性没了。

但 core 仍然干净。 导入 facade 不会加载 server 层, 也不会加载 SDK。只想建模上下文的项目,只付建模的钱。

Plate 02

文件依赖

按实际 import 语句追出来的图。core/ 内部仍是那条干净的 DAG,上面只剩两层。

各层的 __init__.py 没画进去——它们只做 re-export,不参与依赖方向。 注意没有任何一条箭头从上层指回 core:这条约束由一个测试守着, 导入 contexture.core 后检查 sys.modules 里不含任何上层模块。

Plate 03

对象模型

四个 ContextNode 子类共享同一套 route / active 生命周期,而且只有这四个。Role 的每个字段都是"它自己声明的东西"——没有第二条腿。节点知道怎么编译自己;"编译谁、编译到哪一档"由 ref 的形状和调用的是哪个动词决定,而读这两样的是 ContextTree。

这张图删过两轮。v0.0.1 里 Role 挂着 mcp_bindings 和 data_bindings 两条结构同构的授权线;d2a8e66 把后者并进 Resource 消掉一条;ADR 003 把前者整条拿掉——它描述的是"别人家的能力", 而 Contexture 是提供方,不是宿主。

ADR 004 又删了一轮:RoleCompiler 四个类、DisclosureEngine / CapabilityGraph / Ref、RoleRegistry,全部并进 ContextTree。Ref 消失是因为 ref 变成了纯路径 (kubernetes-platform/incident-response/get_pod_logs), split("/") 就是全部解析逻辑——这是"一个角色内成员名跨种类唯一" 这条约束换来的。

Resource 的关键约束不在 route/active 之分,而在 descriptor 与 content 之分:两个编译层级都只吐元数据, 字节只能由 contexture_read 触发 read() 拿到。 列出一百份 runbook 花的是一百行描述,不是一百份文档。

Plate 04

声明式前端 — 一个类体怎么变成 Role

业务用自己的词汇写一个类,框架在类创建时把它变成 Declaration 并校验。出错在 import 时就炸,不等到第一次用。

这没有违背"组合优于继承"。 两个机制回答不同问题: class K8sOperator(Role) 说的是这个节点是什么, children=[...] 说的是它持有什么。继承从不表达包含关系—— 声明式角色协调其他角色时,一样把它们放进 children。

两个 slots 陷阱。 @dataclass(slots=True) 会重建类对象, 于是:① __init_subclass__ 里的零参 super() 抛 TypeError(__class__ 单元格指向被丢弃的旧类);② getattr(cls,'name') 返回槽描述符而非 None。 两处都不是看代码能看出来的,所以在源码里各留了一条注释。

Plate 05

披露成本 — 一次会话到底付了多少

按种类切,不按深度切。角色骨架一次给全因为它便宜,而且看不全兄弟就只能猜;角色里的东西因为贵所以等被打开。这两句是算出来的,不是审美。

交叉点是真的,而且 demo 曾经站在错的一边。 网关不是无条件更省:整片森林的 tool 数明显多于当前任务那一个分支时它才开始赢。 3 个 tool 全在一个分支的 demo 上,原生表面 ≈ 1,055,网关 ≈ 1,500 —— 网关更贵也更慢。 粗算交叉在 8–10 个 tool 且跨多个角色。所以 demo 改成了三个角色: 新读者的第一印象不该正好落在这套论证不成立的那一侧。

披露在一次会话内是单调的。打开过的东西不会再被收回去。 所以省下来的钱是真的,前提是一次会话只走几条分支; 一个把五个域全打开的会话,最终付的和全量常驻一样多——只是分期付。

Plate 06

网关投影 — 为什么表面永远只有五个工具

这是主路的核心转换,也是 v0.1.0 翻转的地方。注册即常驻:协议禁止 tool 列表随连接变化,所以一个被注册的能力是每次会话无论用户问什么都要付的钱。能力要能被推迟,唯一的办法是根本不上表面。

read_only 从"哪个参数"变成"哪扇门",但仍然不是模型能填的。 宿主看不见业务 tool 了,所以没法被逐个告知要不要先问人;但它看得见走的是哪个入口, 而两个入口各自带着对应的 readOnlyHint。 模型可以选错门——选错的结果是被拒绝,不是被执行, 因为宿主的批准决定正是根据那扇门做出的。 这与"read_only 永远不进 input schema"是同一条原则,只是换了位置。 tests/test_stdio_server.py 在真实子进程上双向守着:错的写、错的读、以及一次被允许的写。

代价记在明处。网关自己的返回类型是所有业务 tool 返回类型的并集, 也就是 Any,所以业务 tool 的 outputSchema 在协议层面统一消失了—— GetPodStatus.invoke 标着 -> PodStatus,原生表面上 SDK 会据此产出 structured content,走网关则只剩文本。值还在,协议级的类型没了。 这条有一个测试专门断言它,而不是让它悄悄发生。

还有一条无解的。模型被大量训练过"看着 tools/list 直接发 tool_use", 而"调一个泛化 dispatch 工具"是它没那么熟的模式。ADR 004 把这条列为 medium-high 风险且缓解措施写的是 none:测试能证明机制正确, 证明不了模型愿意导航。

一个真实的坑还在。 @dataclass(slots=True) 做返回类型时, pydantic 会把 slot 描述符读成"不可序列化的默认值"。demo 里的 PodStatus 因此不带 slots,代码旁边有注释写明原因。

Plate 07

谁在跟 Agent 说话 — 一个失败怎么变成一句能照做的话

异常只携带事实,两个读者各自渲染。这不是整洁问题:抛出失败的那一层写不出那句最有用的话——"下一步调 contexture_open"需要网关工具的名字,而 tree 不知道也不许知道。

判据:一个读者的错误,携带句子;两个读者的错误,携带事实。 ModelValidationError / DeclarationError / DuplicateNameError 全部保留散文——它们在声明期和构造期抛出, agent 永远看不到,只有开发者一个读者。需要改的只有 NodeNotFoundError。

LookupFailure 六个成员是穷举的,渲染函数对它逐一分支, 每一支都以"该调哪个工具"收尾——有测试同时守着这两条: 每个 reason 都有渲染,且每条渲染里都出现至少一个网关工具名。 这两个断言在改造前写不出来:分支根本不在一处。

NodeNotFoundError 不再继承 KeyError。那个基类当初是为了 "except KeyError 的老代码还能跑",配套的 __str__ 覆盖则是为了 抵消 KeyError 给参数加引号的行为——散文一上移,这个 hack 的理由就蒸发了。

Plate 08

披露路径 — Agent 怎么在树上走,而服务器不记状态

MCP 2026-07-28 规范原文:tools 列表 MUST NOT 因连接、或因同一连接上的其他请求而变化。所以树不能是协议表面——它得活在 payload 里,而 agent 的位置是它自己带着的那个 ref。

一个进程服务整片森林。 既然树在 payload 里、骨架负责路由, 就没必要在启动时用 --root-role 钉死一个根。 N 个叶子 role 仍然是 1 个进程,不是 N 个。
披露 ≠ 授权,这个区分必须认下来。 ref 现在是可读的路径,agent 完全可以不走导航、直接猜一个 kubernetes-platform/incident-response/get_pod_logs 出来调——你拦不住,也不该拦。 换成可读路径之后这件事从"理论上可能"变成了"经常会发生",这是明知的取舍。

渐进式披露交付的是知识,不是访问权。 tool 能猜着调,但"该按什么顺序看证据""exit 1 和 exit 137 怎么区分""为什么不能先重启"—— 这些只在 contexture_open 之后才存在。 所以验收标准不是"证明 agent 调不到 tool",而是 "证明 Skill 全文与 tool schema 只在被打开之后才进入上下文"。

真正的授权归宿主,而宿主的抓手是那两扇门:一扇带 readOnlyHint,一扇不带。
