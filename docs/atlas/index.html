Plate 00

目录结构

不是一类一文件,是一个内聚概念一文件。 core/ 从八个平铺模块 变成三个子目录,是因为它要装的本来就是三个不同的问题:一个能力是什么、 它在哪、在协议上暴露什么。共享地基(errors / types / constants / principal)留在 core/ 根下不是图省事—— 把它们并进 model/,mcp_interface 就得为了一个异常类去 import model,而那正是它唯一不能有的依赖。

三种节点,没有第四种。 uri 与 mime_type 是协议字段,core 不该知道地址长什么样,所以节点上没有它们—— 要发布一份内容,就在 mcp_interface 里声明一个 Resource 指过去。已经在那儿的内容本身,就是一个无参的只读 Tool。 三种节点因此全都走 route / active 两档,"两档,没有第三档"没有例外。

两个"唯一"是硬约束,不是习惯:cli.py 是唯一写文件系统的模块—— 而且只在 contexture new 生成项目时写,从声明到线上这条路上没有任何模块开过文件; server/ 是唯一 import 官方 SDK 的层。 tests/test_layering.py 用 AST 遍历全包来强制第一条,还顺带确认没有任何模块碰网络; 第二条额外在子进程里真跑一次:import contexture.core 之后 sys.modules 里不许出现 mcp 或 mcp_types—— 两个发行包都查,只查前一个会把间接 import 那条路留着没人看。

Plate 01

分层地图

顶层只有两个词:core 是"是什么",server 是"怎么跑"。core 内部再分三层,其中 mcp_interface 那条依赖省略了 model——协议平面不认识对象模型,这是整张表里最承重的一条。整个 core 不许 import mcp——一个伸手去够线路协议的对象模型,已经不是对象模型了。

为什么 SDK 是硬依赖而不是可选 extra。 2026-07-28 这版协议不小: 取消了 initialize 握手,改成每请求 _meta 协商 + 强制的 server/discover,还得同时服务四个更老的修订。自己扛这些没有回报。 做成硬依赖而不是 [server] extra,是因为 server 现在就是产品本身—— 把产品做成可选自相矛盾。代价写在明处:28 个包、37MB、零依赖属性没了。

但 core 仍然干净。 导入 facade 不会加载 server 层, 也不会加载 SDK。只想建模上下文的项目,只付建模的钱。

Plate 02

文件依赖

按实际 import 语句追出来的图。core/ 内部现在是三簇,而三簇之间只在共享地基上碰头。

各层的 __init__.py 没画进去——它们只做 re-export,不参与依赖方向。 注意没有任何一条箭头从上层指回 core:这条约束由一个测试守着, 导入 contexture.core 后检查 sys.modules 里不含任何上层模块。

Plate 03

对象模型

三个 ContextNode 子类共享同一套 route / active 生命周期,而且只有这三个——"两档,没有第三档"没有例外。Role 的每个字段都是"它自己声明的东西"——没有第二条腿。节点知道怎么编译自己;"编译谁、编译到哪一档"由 ref 的形状和调用的是哪个动词决定,而读这两样的是 ContextTree。

三种节点,不是四种。 Role 递归组合,Skill 装过程知识, Tool 装可执行能力——三种全都走 route / active 两档。已经在那儿的内容 不是第四种节点,它就是一个无参的只读 Tool:两次调用返回同样的 字节,什么也不从参数算。列出一百份 runbook 依然只花一百行描述——卡片是卡片, 正文只有真去 invoke 才来。

整棵树只有一个运行时类:ContextTree。 没有编译器、 没有注册表、没有 Ref 类型。ref 是纯路径 (kubernetes-platform/incident-response/get_pod_logs), split("/") 就是全部解析逻辑——这是"一个角色内成员名跨种类唯一" 这条约束换来的。

URI 属于协议平面,不属于节点。 想让宿主在 resource 原语上取到 同一份内容,就在 mcp_interface 里声明一个 Resource 指过去。 一个能力两个地址,而不是两份声明——两条路读到的永远是同一个节点。

Plate 04

声明式前端 — 一个类体怎么变成 Role

业务用自己的词汇写一个类,框架在类创建时把它变成 Declaration 并校验。出错在 import 时就炸,不等到第一次用。

这没有违背"组合优于继承"。 两个机制回答不同问题: class K8sOperator(Role) 说的是这个节点是什么, children=[...] 说的是它持有什么。继承从不表达包含关系—— 声明式角色协调其他角色时,一样把它们放进 children。

两个 slots 陷阱。 @dataclass(slots=True) 会重建类对象, 于是:① __init_subclass__ 里的零参 super() 抛 TypeError(__class__ 单元格指向被丢弃的旧类);② getattr(cls,'name') 返回槽描述符而非 None。 两处都不是看代码能看出来的,所以在源码里各留了一条注释。

Plate 05

披露成本 — 一次调用只看一层

一层总是给全,因为看不全兄弟就只能猜;但只给这一层。规则作用于一层兄弟,不作用于整棵树:6 个角色时这两者是同一个东西,11,111 个角色时后者装不进 context window。

「广度」和「广度 × 深度」是两回事。 规则的原文是 every sibling is visible before the choice——它要求的是 一层兄弟,不是一棵子树。小树上这两者看起来是同一个东西, 这正是它容易被外推成后者的原因;它不能被这样外推。

换来的代价,两条,都是真的。 一、到第 d 层要 d 次往返才开始干活,小树因此略贵(表里 0.9× 那两行)。 二、角色的 description 必须能替它整棵子树做路由—— agent 在兄弟之间选的时候看不见孙辈了。第二条刻意不用机制解决: 给卡片加子树摘要或计数,是在补一句没写好的描述的锅。

bootstrap 里的 roster 是另一回事,故意不一样。 它不花往返,所以小森林不妨一次给全;它按广度优先走, 因为 roster 是会被预算截断的东西——深度优先的截断会把 1200 字全花在一条深脊上, 而根的其他子角色一个都不提,对只负责路由的文字来说是最坏的答案。

披露在一次会话内是单调的。打开过的东西不会再被收回去。 省下来的钱是真的,前提是一次会话只走几条分支; 一个把所有域全打开的会话,最终付的和全量常驻一样多——只是分期付。

Plate 06

网关投影 — 为什么模型那一侧永远只有四个工具

这是主路的核心转换。注册即常驻:协议禁止 tool 列表随连接变化,所以一个被注册的能力是每次会话无论用户问什么都要付的钱。能力要能被推迟,唯一的办法是根本不上表面。

read_only 从"哪个参数"变成"哪扇门",但仍然不是模型能填的。 宿主看不见业务 tool 了,所以没法被逐个告知要不要先问人;但它看得见走的是哪个入口, 而两个入口各自带着对应的 readOnlyHint。 模型可以选错门——选错的结果是被拒绝,不是被执行, 因为宿主的批准决定正是根据那扇门做出的。 这与"read_only 永远不进 input schema"是同一条原则,只是换了位置。 tests/test_stdio_server.py 在真实子进程上双向守着:错的写、错的读、以及一次被允许的写。

代价记在明处。网关自己的返回类型是所有业务 tool 返回类型的并集, 也就是 Any,所以业务 tool 的 outputSchema 在协议层面统一消失了—— GetPodStatus.invoke 标着 -> PodStatus,原生表面上 SDK 会据此产出 structured content,走网关则只剩文本。值还在,协议级的类型没了。 这条有一个测试专门断言它,而不是让它悄悄发生。

还有一条无解的。模型被大量训练过"看着 tools/list 直接发 tool_use", 而"调一个泛化 dispatch 工具"是它没那么熟的模式。ADR 004 把这条列为 medium-high 风险且缓解措施写的是 none:测试能证明机制正确, 证明不了模型愿意导航。

一个真实的坑还在。 @dataclass(slots=True) 做返回类型时, pydantic 会把 slot 描述符读成"不可序列化的默认值"。demo 里的 PodStatus 因此不带 slots,代码旁边有注释写明原因。

Plate 07

谁在跟 Agent 说话 — 一个失败怎么变成一句能照做的话

异常只携带事实,两个读者各自渲染。这不是整洁问题:抛出失败的那一层写不出那句最有用的话——"下一步调 contexture_open"需要网关工具的名字,而 tree 不知道也不许知道。

判据:一个读者的错误,携带句子;两个读者的错误,携带事实。 ModelValidationError / DeclarationError / DuplicateNameError 全部保留散文——它们在声明期和构造期抛出, agent 永远看不到,只有开发者一个读者。需要改的只有 NodeNotFoundError。

LookupFailure 六个成员是穷举的,渲染函数对它逐一分支, 每一支都以"该调哪个工具"收尾——有测试同时守着这两条: 每个 reason 都有渲染,且每条渲染里都出现至少一个网关工具名。 这两个断言在改造前写不出来:分支根本不在一处。

NodeNotFoundError 不再继承 KeyError。那个基类当初是为了 "except KeyError 的老代码还能跑",配套的 __str__ 覆盖则是为了 抵消 KeyError 给参数加引号的行为——散文一上移,这个 hack 的理由就蒸发了。

Plate 08

披露路径 — Agent 怎么在树上走,而服务器不记状态

MCP 2026-07-28 规范原文:tools 列表 MUST NOT 因连接、或因同一连接上的其他请求而变化。所以树不能是协议表面——它得活在 payload 里,而 agent 的位置是它自己带着的那个 ref。

一个进程服务整片森林。 既然树在 payload 里、逐层披露负责路由, 就没必要在启动时用 --root-role 钉死一个根。 N 个叶子 role 仍然是 1 个进程,不是 N 个。
披露 ≠ 授权,这个区分必须认下来。 ref 现在是可读的路径,agent 完全可以不走导航、直接猜一个 kubernetes-platform/incident-response/get_pod_logs 出来调——你拦不住,也不该拦。 换成可读路径之后这件事从"理论上可能"变成了"经常会发生",这是明知的取舍。

渐进式披露交付的是知识,不是访问权。 tool 能猜着调,但"该按什么顺序看证据""exit 1 和 exit 137 怎么区分""为什么不能先重启"—— 这些只在 contexture_open 之后才存在。 所以验收标准不是"证明 agent 调不到 tool",而是 "证明 Skill 全文与 tool schema 只在被打开之后才进入上下文"。

真正的授权归宿主,而宿主的抓手是那两扇门:一扇带 readOnlyHint,一扇不带。

Plate 09

服务与身份 — 谁在调用,到哪为止

同一片森林,stdio 起是本机的一个子进程,streamable HTTP 起是网络上的一个端点。换传输不改变声明里的任何一个字。变的只有一件事:网络上的调用者带着一张票来,于是"谁在调用"第一次成为一个真问题——而框架对这个问题的回答,止于把答案交出去。

身份是 contextvar,不是参数。 官方 Python SDK、FastMCP、mcp-go 各自独立得出同一个结论:身份是请求的属性, 不是某个函数签名的属性。做成参数,等于给每一个根本不关心调用者是谁的能力 都加一个它用不到的形参。Principal 上也不带原始 token—— 规范禁止把客户端的票透传给上游,框架拦不住,但可以不提供便利:真要透传, 得绕过 contexture 伸手去够 SDK,那在 review 里是看得见的动作。
无状态不是配置项,是立场。 2026-07-28 之后协议没有会话,open(ref) 是 ref 的纯函数, 服务器不记任何每连接状态——所以任意副本能答任意请求, 负载均衡后面不需要黏性会话。stateless_http 因此钉死 True, 连逃生口都不给:能关掉它,就等于能让上面那句话在不报错的情况下变成假的。
框架给身份,不给权限——代价写在明处。 没有 required_scopes 挂在 tool 上,没有按调用者过滤披露。 一个调不动某能力的人,照样看得见它的卡片:名字、描述、参数 schema。 公网部署时,能力图谱是公开的。
